# skillar.sh UX 2단계 "왜" 문서 (G1)

상태: 회장님 검토용 초안 v2 (OWNER REVIEW POINT 1). 이 문서 승인·수정 전에는 화면 작업(G2 이후)을 시작하지 않습니다.

v2 변경 (11-16, 이연 리뷰 반영): J2를 드롭오프(후보→읽기) 중심으로 재작업하고 첫 화면 헤드라인 수치를 바꿨습니다. 근거는 이연이 전달한 11/13 분석 패키지(방법론·집계만 공유, 원시 로그 비공개)를 우리가 직접 검토한 것이며, 방향 설정을 위한 설계 가설의 근거로만 씁니다.

## 1. 왜 다시 하는가

11-05 회장님 요구(R25)는 "랭퓨즈가 왜 그렇게 설계했는지 추측해서 가져올 수 있는 패턴을 최대한 적용"과 "사용자의 페르소나·경험·여정에서 이상적 상태 정의"였고, R26(컴포넌트 그대로)은 그 수단입니다(11-16 결정 6). Phase B(#99~#108)는 수단을 목표로 삼아 픽셀 일치를 검사 기준으로 삼았고, 11-12 평가는 "하 개판이네"였습니다. 그래서 2단계 재실행의 기준은 컴포넌트 일치가 아니라 **사용자 과업**입니다. 판정은 전부 눈으로 확인 가능한 결과(1440px·390px 캡처, 클릭 수, 키보드 이동)로 합니다.

## 2. 페르소나

**1차: 여러 코딩 에이전트를 굴리는 개발자(회장님).** Claude Code·Codex·Gemini 등 여러 실행 환경이 스킬을 검색하고 읽습니다. 가장 자신 있는 질문은 "어제 그 세션에서 어떤 스킬 어떤 버전을 읽었고, 그 뒤 어떻게 됐지?"이고, 그다음은 "검색이 후보를 찾고도 왜 읽기로 이어지지 않았지?"입니다. 주 사용자는 당분간 회장님과 회장님의 에이전트로 한정합니다(11-16 결정 5). 과금·팀 기능은 미룹니다.

**2차: 회장님의 에이전트(MCP 클라이언트).** 화면이 아니라 MCP로 검색·등록·조회합니다. 화면은 에이전트가 남긴 기록을 사람이 오해 없이 읽는 곳입니다.

공통 성질: 기록의 단위는 "요청"이고 세션은 요청의 모음입니다. 검색과 읽기를 따로 판정하고(11/02 확정 상태 모델, R06), 기록이 없다고 실패·취소로 추정하지 않습니다.

## 3. 핵심 여정과 이상적 끝 상태

각 여정의 "현재"는 main 89212c3 기준이며, G3에서 전후 클릭 수와 소요를 캡처와 함께 기록합니다.

### J1. 세션을 열어 어떤 스킬·버전을 읽었고 결과가 어땠는지 안다 (가치 1)
- 시작: 대시보드 첫 화면.
- 이상적 끝 상태: 첫 화면이 최근 세션 목록이고, 각 행이 읽은 스킬(이름·버전/다이제스트)과 검색·읽기 요청 결과를 보여 줍니다. 세션 하나를 열면(≤2클릭) 대화 차례별로 어떤 스킬의 어떤 버전을 읽었는지와 요청별 상태(11/02 MECE 값)가 보입니다.
- 판정: 첫 화면에서 답까지 ≤2클릭, 데스크톱·390px 모두.

### J2. 검색이 후보를 찾고도 읽기로 이어지지 않은 세션을 골라낸다 (가치 3의 출발점)
- 근거로 전달받은 관찰 (이연 11/13 분석 패키지가 보고한 값, 원시 로그 비공개·재현 불가): 단일 사용자의 Dori/OMO 세션 294개 JSONL(로그 보존 범위, 대략 11/06~11/13) 중 skillar 세션 25개, 검색 37회(후보 있음 35, 없음 2), 후보 있는 검색에 읽기가 귀속된 경우 5회, 읽힌 후보는 모두 1순위, 후보 목록 밖 읽기 0건. Codex·Claude Code 로그와 호스팅 트레이스는 빠져 있고 출력이 잘린 검색은 제외됐다고 보고합니다.
- 코드에서 확인한 방법론: 집계 스크립트는 세션 전체의 읽기 URI 집합을 검색 후보와 시간 순서 없이 대조합니다. 검색보다 먼저 일어난 읽기도 귀속되고 한 읽기가 여러 검색에 중복 연결될 수 있습니다. 잘린 출력 제외·타 클라이언트 제외·재현 미실시이므로, 이 표본에서 전체 사용의 전환 상한이나 이탈 하한을 증명할 수는 없습니다.
- 설계 가설: 이 제한된 관찰에서 "후보 없음"(2/37)보다 "찾았는데 안 읽음"이 더 자주 관찰됐으므로, "못 찾음"보다 "찾았는데 안 읽음"을 먼저 보여 주는 편이 낫다는 가설을 세웁니다. 전체 사용의 병목이라고 확정하지는 않습니다.
- 주의: 읽기로 이어지지 않았다고 해서 실패는 아닙니다. 검색 응답의 후보 설명만으로 판단이 끝날 수 있고, 11/02 확정 원칙은 기록 부재로 실패·취소를 추정하지 않는 것입니다. 그래서 이 수치는 "실패율"이 아니라 **전환율과 진단의 출발점**으로 표시하고, 카피 어디에도 이탈을 실패로 라벨링하지 않습니다.
- 이상적 끝 상태: 대시보드 요약의 헤드라인 수치가 "후보→읽기 전환"입니다. 이 지표에는 귀속 기준이 필요합니다: 같은 세션 안에서 후보를 표시한 검색 요청보다 뒤에 일어난, 그 후보와 같은 스킬의 첫 읽기 요청 1건에만 귀속합니다(시간 순서 적용·중복 귀속 금지). 위 집계 스크립트는 이 기준을 만족하지 못하므로 UI 지표는 그 집계를 재사용하지 않고 이 기준으로 새로 계산합니다. 세션 목록 필터에서 "후보 있음·읽기 없음" 한 번으로 해당 세션만 남고, 세션을 열면 어떤 후보가 표시됐고 무엇을 읽었는지(또는 읽지 않았는지)가 보입니다. 보조 진단으로 "검색 결과: 후보 없음" 필터와 이유 라벨(empty_query/no_overlap/below_threshold/explicit_only)은 그대로 둡니다(이연 요약 표본에서는 37회 중 2회였지만, 발생 때 원인이 바로 읽혀야 합니다).
- 판정: 첫 화면에서 전환 수치가 보임, 필터 1회 적용으로 대상 세션 목록 도달, 이탈을 실패로 부르는 카피가 없음.

### J3. 한 스킬의 두 버전 사이 결과를 비교한다
- 이상적 끝 상태: 스킬 상세에서 버전별 읽기 요청 수·결과(성공/실패/알 수 없음)와 세션 목록이 갈리고, 두 버전을 골라 같은 기간의 지표를 나란히 봅니다. 평가 데이터는 아직 0건이라(R10) 승격 UI는 만들지 않고, 비교의 자리만 확보합니다.
- 판정: 스킬 상세 진입 → 두 버전 비교 화면까지 ≤3클릭.

### J4. 첫 로그인 뒤 에이전트를 연결한다
- 이상적 끝 상태: 첫 화면이 빈 상태를 숨기지 않고 "아직 기록이 없음"을 명시하며, 다음 행동(에이전트 연결: MCP 등록 안내)으로 한 칸 안내합니다. 연결·권한 관리는 그 자체의 탭/섹션으로 물리고, 첫 화면의 주인공은 세션 기록입니다(G3 방향: 연결 관리가 세션 추적을 앞서지 않음).
- 판정: 로그인 → 연결 안내 도달 ≤2클릭, 빈 상태 문구가 오류처럼 읽히지 않음.

### J5. 랜딩에서 가입까지
- 이상적 끝 상태: 랜딩 첫 화면이 "스킬 서빙 + 세션 트레이스" 가치를 실제 대시보드 화면(세션→스킬 버전→결과)으로 보여 주고, Google 로그인까지 한 흐름입니다. 근거 없는 지표·가짜 로고·AI 생성 이미지는 쓰지 않습니다(11-03 원칙).
- 판정: 랜딩 → Google 로그인 버튼 ≤1클릭, 11-05 불만(탐색·로그인·대시보드·랜딩 "보기 싫음") 각각에 전후 캡처 대응.

## 4. Langfuse에서 가져오는 패턴과 그 이유

각 패턴에 "왜 랭퓨즈가 그렇게 했을까"의 추측과, 그것이 돕는 여정을 붙입니다. 컴포넌트·픽셀 일치는 목표가 아니라 참고 증거입니다.

1. **트레이스 우선 정보 구조** (세션 → 트레이스 → 관측 계층). 추측한 이유: 관측 도구의 사용자는 "실행 하나"를 디버깅하러 오므로, 계정·설정이 아니라 기록이 첫 화면의 주인공이어야 합니다. → skillar 적용: 세션 → 요청(검색/읽기) → 스킬 버전. J1, J4를 돕습니다.
2. **목록에서 여는 사이드 상세(피크) 패널** (세션 목록에서 턴 클릭 → 사이드 패널로 트레이스). 추측한 이유: 목록 문맥을 잃지 않고 여러 항목을 연속으로 조사하게 하려고. → 이미 있는 peek을 J1의 기본 진입으로 다듬습니다. J1, J2.
3. **밀도 높은 테이블과 패싯 필터**. 추측한 이유: 수백 건의 기록에서 "조건에 맞는 것만"을 스캔하는 작업이 주 사용이라 열 선택·밀도·패싯이 핵심 도구입니다. → J2의 필터 경험 기준으로 삼습니다.
4. **평가 점수를 기록 옆에 인라인 표시(scores)**. 추측한 이유: 사람의 판정을 기록과 같은 화면에 두어야 개선 루프가 돌기 때문입니다. → R10 승격 기능의 자리로 예약만 합니다(지금 만들지 않음). J3.
5. **세션 리플레이(시간 순 대화 흐름)**. 추측한 이유: 결과만이 아니라 순서가 원인 분석에 필요하기 때문입니다. → skillar의 대화 차례(turn) 뷰에 대응. J1.
6. **빈 상태를 숨기지 않는 표현**. 추측한 이유: 관측 플랫폼은 수집 전이라 "없음"이 정상이라, 빈 화면을 오류처럼 보이게 하면 신뢰를 잃기 때문입니다. → 11/02 "로그 없다고 실패·취소 추정 금지"와 같은 결론. J4.

## 5. 화면별 이상적 끝 상태 (요약)

- **랜딩**: J5. 가치 1을 화면 자체로 설명, 가입 한 흐름.
- **로그인**: Google 한 버튼, 동의 범위를 짧게 명시(현재 수준 유지, 배치만 정리).
- **호스팅 대시보드 홈**: 최근 세션 → 스킬+버전 → 결과 순. 요약 수치의 헤드라인은 "후보→읽기 전환"(J2). 연결·권한 관리는 별도 탭/아래 섹션(G3).
- **세션 목록**: 검색/읽기 요청 요약과 11/02 상태 필터만. 세션 단일 "상태" 없음(#109로 정리됨).
- **세션 상세(트레이스)**: 대화 차례별 읽은 스킬·버전·요청 상태. 사이드 피크 우선.
- **흐름(Sankey)**: 검색/읽기 요청 단위와 11/02 상태만(#109로 정리됨).
- **스킬 상세·버전**: 버전별 비교의 자리(J3).
- **로컬 대시보드**: 같은 정보 구조와 라벨을 유지(호스팅과 용어 일치).

## 6. 판정과 멈춤 규칙

- 각 목표는 구현 뒤 게이트를 돌리고, 실패하면 그 목표 안에서 2회까지 고치고 3회 실패 시 근거와 함께 보고(회장님 원칙: 미리 조사 부족으로 멈추지 않음).
- 수용 기준은 캡처(1440px·390px), 전후 클릭 수, 키보드만으로 J1~J5 통과, axe 신규 serious/critical 0건.
- 머지·배포는 이연이 검토·결정(11-16 회장님 위임). 이 단계 산출은 초안 PR과 미리보기까지.
