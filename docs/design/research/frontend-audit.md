# Skillar web UI: frontend reference and Impeccable audit

Audit date: 2026-11-02. Advisory only. The only written artifact is this report. No product files, dependencies, settings, or reference files were changed.

## Decision for the reviewed plan

**Extend the existing workshop design into an honest, empty product preview. Do not redesign the identity, simulate authentication, invent connected state, or populate a fictional dashboard.**

The owner's latest decisions are the controlling contract:

- Preserve `site/DESIGN.md`: workshop artwork, warm neutral surfaces, vermilion actions, Arial/system typography, square controls, readable code, light/dark themes, and restrained motion.
- Show a genuinely disabled GitHub sign-in control, with an enabled, separately named preview action. Preview is not authentication.
- No email, password, token, or arbitrary-endpoint inputs.
- Connect presents a fixed `.example` MCP configuration. It is an illustrative, non-working configuration, not a connection attempt or evidence of success.
- Dashboard has four EMPTY views using the existing taxonomy: **Sessions, Workspaces, Flow, Heatmap**. No fixture metrics, fake rows, example usage charts, invented users, or fabricated live status.

Taxonomy is source-backed: `local/dashboard/main.tsx:110-115` defines those exact four labels; `local/dashboard/main.tsx:140-152` uses navigation links with `aria-current` and dispatches the views. `local/dashboard/DESIGN.md:123-129` documents the same taxonomy. Only the cited taxonomy portions were inspected; this is not an audit of the separate local Preact application.

The current `/site` snapshot is a static landing page. `site/src/main.ts:1-40` implements theme choice, install-command copying, and a setup-example select. It contains no hosted login, account connection, or dashboard implementation. The connect section at `site/index.html:92-102` is local CLI documentation, not a hosted connect screen. Missing future screens are a scope/baseline fact, **not a bug or a failed authentication implementation**.

## Findings: current source, ranked by user impact

No P0 blocker or verified WCAG AA failure is established by this source-only audit. The following four P2 issues have concrete source evidence. They are existing usability or contract issues, not claims that the proposed preview has already been implemented.

### F1. P2: the prominent acquisition action leads to a dead end

- Evidence: `site/index.html:41` labels the hero action "Get your skill server" and points to `#get-server`. Its destination has a disabled email field and disabled button at `site/index.html:138-142`. The adjacent notes at lines 44 and 142 disclose that hosting is unavailable.
- Impact: the strongest action promises acquisition but only scrolls to an unavailable form. A visitor can read the caveat, but cannot complete that action. GitHub remains a working alternative.
- Recommendation under the owner's decision: make the enabled action describe the actual preview outcome; keep real GitHub sign-in visibly unavailable with an adjacent explanation. Replace the email-form scaffold rather than enabling it. Do not make the same button sometimes authenticate and sometimes silently enter preview.
- Guidance: Impeccable `skill/reference/clarify.md:20-35` requires the current fact, available next action, and action/outcome agreement; `skill/reference/onboard.md:3,37-40` prioritizes first value and access.
- Verification: keyboard and pointer activation of the enabled preview action reach the explicitly labeled preview. The disabled GitHub control initiates no navigation, OAuth request, popup, or account state. No email/password/endpoint input exists in the product flow.

### F2. P2: the install shortcut omits the upgrade prerequisite at the decision point

- Evidence: `site/index.html:45-47` offers the global install command without distinguishing fresh installation from upgrade. The migration warning is inside the FAQ at `site/index.html:127`. Root `README.md:21-26` explicitly says both packages own the `gisool` command, a direct global install collides, and migration must precede installation.
- Impact: an existing gisool user can copy the most prominent command before encountering the prerequisite.
- Recommendation: retain the install example but identify it as a fresh install and place the migration link beside it. This changes decision context, not product behavior or brand direction.
- Guidance: Impeccable `skill/reference/clarify.md:7-16,63-65`; local `references/designpowers/vendor/skills/cognitive-accessibility/reference.md:43-46`.
- Verification: a user reading only the install block can distinguish fresh setup from migration and find the migration guide before copying/installing. Check the command against the repository; do not run a global installation as UI QA.

### F3. P2: the foreground alternative drops a required setup distinction

- Evidence: `site/index.html:94-101` presents `skillar init`, followed by "Prefer a foreground process? skillar serve". Root `README.md:32` specifies `skillar init --no-service`, then `skillar serve`, and explains that ordinary init installs a background service.
- Impact: the alternative is underspecified beside a service-installing sequence. A reader can follow the default setup and then attempt a foreground daemon without understanding the service distinction.
- Recommendation: show the foreground alternative as the complete documented sequence, or link to that exact explanation. Do not imply both daemon modes should be started together.
- Guidance: Impeccable `skill/reference/clarify.md:7-16,63-65`; local cognitive-accessibility guidance above.
- Verification: the foreground branch matches the repository's documented commands and clearly replaces, rather than follows, the background-service branch. This is a documentation comparison, not a claim that a daemon conflict was reproduced.

### F4. P2: the home wordmark lacks the design contract's minimum target

- Evidence: `site/index.html:26` is the home link. `site/src/style.css:28` sets a 32px font with line-height 1 and no padding or minimum target height. Other navigation/actions explicitly receive target padding or minimum heights at `site/src/style.css:31,33,44,122`. `site/DESIGN.md:53` requires targets of at least 44px.
- Impact: the source-defined wordmark line box is smaller than the project's target-size contract.
- Recommendation: enlarge the link's hit area without enlarging the wordmark or altering its visual identity.
- Qualification: this is a project-contract finding. It is **not automatically a WCAG 2.5.8 failure**: that AA criterion uses 24 CSS px and exceptions; 44px is the project's stronger requirement. Actual bounding rectangles were not measured in a browser.
- Verification: the home link's clickable rectangle is at least 44 by 44 CSS px at all target widths, without overlapping adjacent targets; its focus indicator remains visible.

## Requirement deltas for the planned screens

These are prospective acceptance requirements, not invented defects in nonexistent code.

1. **Update the existing design contract before implementation.** `site/DESIGN.md:37-45` currently defines landing primitives only; lines 55-57 document unimplemented hosted accounts. Add the disabled-auth/preview distinction, preview notice, read-only example-config panel, navigation/current state, copy success/failure, and four distinct empty states. Preserve existing tokens and accepted no-backend boundary; do not regenerate a new brand system.
2. **Login:** one plain heading, disabled GitHub action, nearby reason, and a separate enabled "Explore preview" or equivalent truthful action. No credential form or pretend user identity.
3. **Connect:** label the fixed `.example` configuration as illustrative before its copy action. Copy means "example copied", never "connected". No endpoint editor, credential field, connection probe, token storage, fake spinner, or manufactured connection success.
4. **Dashboard:** retain Sessions / Workspaces / Flow / Heatmap in that order. Each view explains what belongs there and why this preview has no data. Navigation is usable even when data is empty. Do not substitute four equal decorative metric cards for the four actual views.
5. **Empty is not loading, error, or zero-valued telemetry.** Prefer a short explanatory empty state over blank charts, disabled filter scaffolding, skeletons that never finish, or numeric metrics. A heatmap full of zero cells still implies measured activity; omit it in this preview.
6. **Preview remains visibly preview across navigation and reload.** Neither a fake avatar nor "signed in", "connected", "live", "synced", or successful provisioning language may appear as an asserted state.

The proposed disabled GitHub + separate preview is intentional. Generic advice to "make every CTA work" must not enable GitHub or invent auth. The same applies to onboarding guidance that suggests creating a first item or showing example data: no such action or data is authorized here.

- **Present, low priority:** generic benefit headings "Less setup. More doing." (`site/index.html:93`) and "Make room for better skills." (`site/index.html:137`) could fit unrelated products. Use the heading's space to name the local setup task or truthful preview outcome. This is a content-specificity opportunity, not evidence that the whole design is generic.

They are hidden from assistive technology and paired with text. Do not elevate this stylistic match above F1-F4 or declare it an accessibility failure.
- **Not found in inspected source:** fake customer logos, fabricated social proof, made-up usage metrics, gradient headline text, repeated icon-heading-description card grids, gratuitous animation, or accent side-stripes on rounded cards. The real repository excerpt (`site/index.html:80-87`), ordered workflow (`69-73`), meaningful workshop illustration (`51-54`), comparison table (`108-117`), and native disclosures (`126-131`) are product-specific evidence against a broad "AI slop" verdict.
- **Prevent in the new work:** fabricated populated dashboards, green connected/live badges without a connection, simulated GitHub success, arbitrary endpoint forms, and empty ornamental charts. Impeccable `craft-floor.md:37,49` directly supports rejecting decorative data chrome and dishonest configuration.

### Conflicts and rejected alternatives

- `design/taste-skill.md:8-9` explicitly limits itself to landing/portfolio/redesign work, **not dashboards, data tables, or multi-step product UI**. It is not the primary dashboard reference even though the frontend router calls it a general operational default elsewhere.
- `design/gpt-tasteskill.md:65` suggests page-wide overflow hiding. Reject it as a repair for clipped or oversized product content; fix sizing/containment and preserve access instead.
- Font bans, a universal need for dimension/glass, full hero animation, comp-generation gates, and "signature move" demands do not override the owner's existing workshop contract. In particular, Impeccable `craft-floor.md:12,39,45` conflicts with existing system typography/tight hero tracking; do not manufacture a violation from this conflict.
- Native controls are useful here. Do not replace selects, links, buttons, or disclosures solely to mimic a catalog.
- The React tooling gate is **inapplicable**: `site/package.json:1-15` lists Vite and TypeScript, not React; local `design/react-dev-tooling-skill.md:198-202` explicitly excludes non-React projects. The separate local dashboard's Preact stack does not change `/site`.
- New imagery, Lazyweb browsing, beui/react-bits effects, and native-platform implementations are not prerequisites for this scoped preview. Their local reference documents were still read.
- Brand files often describe a site's behavior speculatively (for example, `opencode.ai.md:217-220` says focus "likely" uses an outline). Treat them as secondary inspiration, not standards or proof of accessibility.
- Do not conflate a style recommendation with a WCAG requirement. For example, the local responsive reference associates 200% zoom with SC 1.4.10; test 200% text resizing and 320 CSS px reflow separately. A 16px body recommendation is not itself a universal WCAG pass/fail threshold.

## Strongest counter-case considered

The strongest objection to F1 is that unavailable hosting is already disclosed both beside the hero action and at its destination, and preserving that honesty is explicitly required by `DESIGN.md`. That rules out calling it deceptive or demanding a functioning account service. F1 therefore remains P2 action/outcome friction, addressed by the owner's separate enabled preview, not by enabling signup.

The strongest objection to a broad aesthetic critique is the existing, coherent workshop system plus actual repository content. The source supports that objection. This audit recommends narrow clarity/accessibility fixes and a restrained extension, not brand mimicry.
